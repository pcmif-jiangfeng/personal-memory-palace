# Task12 J3 — 账号删除前置检查检测报告

日期：2026-09-29。范围仅 J3；保留前序 G/H/I/J1/J2 改动，不进入 J4，不提交、推送或部署。正式站未改变。

## 结论

已实现只读的账号删除前置检查，覆盖当前账号名下所有 Museum，而不是仅检查默认馆或当前选中的馆。

- 任意自有馆仍有有效协作者：不能进入删除流程，提示先转移对应馆长身份。
- 所有自有馆均无有效协作者，或已无自有馆：该前置条件通过。
- “通过”仅表示符合 J3 条件。没有发起 30 天待删除、没有实际删除，也没有开放删除提交按钮。

## 实现与边界

- 账号设置和没有自有馆时的 Onboarding 页面新增“检查账号删除条件”入口，进入 `/account/deletion`。
- 新增 `GET /api/account/deletion-preconditions`，由真实 User Session 推导检查对象，只允许当前已验证用户读取自己的结果。匿名 API 返回 401、页面跳转登录；底层查询也重新检查用户存在及邮箱验证状态。
- 新增 `checkAccountDeletionPreconditionsInDatabase`，使用同一短事务取得一致的用户、汇总和名单快照。业务 SQL 只有 SELECT，不更新账号、馆、关系、Session、内容或审计。
- 汇总检查所有 `owner_id` 为当前用户的 Museum，不因列表分页、馆状态或默认选择而漏掉阻塞馆。名单每页最多 25 座，按 `created_at,id` 稳定排序；分页外的阻塞馆仍令整体结果不通过。
- 有效协作者指非馆长自身、role 为 collaborator、status 为 active 的成员关系。revoked 关系不阻塞；异常的 Owner 自身成员记录不当作协作者。已加入但不是自己拥有的馆不纳入删除范围，也不泄露其名称。
- 已有 active 关系的协作者即使暂时取消邮箱验证，仍阻塞检查，不通过改变验证状态绕过所有权责任。pending_deletion 馆仍按保留的成员关系检查；本步不改变其状态，也不实现取消删除。
- 返回字段限于是否可进入流程、原因、总自有馆数、阻塞馆数、分页信息及本页自有馆的 ID、名称、馆址、状态、有效协作者人数，不包含成员邮箱、密码、Session、私人正文或照片。
- 查询只允许 page 参数，重复 page、非法分页、传入 userId 或 museumId 过滤都被拒绝，不能改为检查别人的账号或只检查一座馆。成功 API 响应为 `private, no-store`，页面与 API 均动态查询。
- 页面明确说明这是前置检查，展示阻塞馆的既有 J2 转移入口；非 active 馆不生成无法使用的设置/转移链接，而提示后续先处理馆状态。
- 没有新增数据库迁移、删除计划字段、定时任务、永久删除操作或依赖。新接口只实现 GET；POST、DELETE、PATCH 均返回 405。

### 真实本地 HTTP 验收

执行 `node --experimental-strip-types scripts/verify-account-deletion-preconditions.mjs`，仅使用回环地址、新建临时数据库和合成 Session：

1. 匿名 API 401，匿名页面跳转登录。已验证用户检查自己的结果；配置为平台管理员的无自有馆账号仍只得到自己的空结果。
2. 当前账号拥有两座馆，仅第二座有协作者，检查仍不通过；请求没有条目的第二页，汇总仍保持阻塞，不因分页变为通过。
3. 结果和页面不泄露其他用户 Museum 的名称、密码或私人 Memory 哨兵；页面显示“必须先转移”及对应馆转移链接，并明确不会发起待删除。
4. 协作者账号只检查其自己的馆；无自有馆账号得到通过结果，并能从 Onboarding 找到入口。
5. 非法/重复 page、userId 或 museumId 参数，API 400、页面 404；POST、DELETE、PATCH 请求均 405。
6. 上述全部请求后，数据库业务快照完全不变，无账号/馆/Session 删除、状态修改或检查成功审计。
7. 在临时站真实调用 J2 完成第二座馆转移并保留原馆长为协作者后，重新读取：原馆长只剩一座无协作者的自有馆，检查通过；新馆长拥有两座馆，因保留原馆长的 active 协作关系而被阻塞。每次检查均按最新关系重新计算。
8. 转移后的检查请求仍不写数据，账号和 Museum 数量保持不变，私人 Memory 原文保持不变。测试服务已停止，临时数据库、账号与构建目录已清理，未访问生产环境。
