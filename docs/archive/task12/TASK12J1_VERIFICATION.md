# Task12 J1 — 馆长移除协作者检测报告

日期：2026-09-29。范围仅 J1，未进入 J2。

## 结论

已实现馆长移除指定协作者。移除成功后，该馆的成员权限立即失效；对方刷新或重新切换时，Museum 不再出现在 Switcher；旧会话下一次私人内容请求被拒绝。馆内内容、其他协作者及其他 Museum 保持不变，移除有可信审计。

## 实现及行为

- 馆长账号页新增“管理协作者”，进入 `/account/museums/[id]/collaborators`。只显示本馆有效协作者的 ID、显示名称和邮箱，每页最多 25 条；分页参数严格校验。密码、私人内容及其他馆成员不进入列表。
- 每位协作者有明确后果说明、确认勾选及“移除协作者”按钮。成功后刷新名单，失败时显示可理解的错误。
- `DELETE /api/museums/[id]/collaborators/[userId]` 要求同源、有效已验证 User、当前 Museum Owner 身份和 `{ "confirm": true }`；不接受客户端伪造 actor 等额外字段。
- 身份从真实 Session 推导，事务内重新验证馆长及 Museum active 状态。协作者、无关用户及没有馆长身份的 Platform Admin 均不能执行；不能通过此入口移除馆长自身。
- 仅将指定 `(museum_id,user_id)` 的 membership 从 active 改为 revoked，保留关系和建立时间。重复调用保持已有撤销时间，不重复记事件；不存在的关系返回 404。
- `membership.remove` 审计记录实际馆长 actor、目标 Museum、目标成员 objectId、时间及 active → revoked 的最小 diff。审计失败或成员写入失败时整笔事务回滚。
- 复用现有逐请求 Museum/Memory/Photo 权限检查和 Switcher 有效成员筛选，不缓存被移除者的授权。异步照片保存后的提交也重新检查身份，不能因提前拿到 scope 而绕过移除。
- 不删除 User、Museum、Memory、Stage、Photo 或其他成员，不改变内容版本或存储配额；无新增数据库迁移、无新增依赖。

### 真实本地 HTTP 验证

执行 `node --experimental-strip-types scripts/verify-collaborator-removal.mjs`，只使用临时数据库、合成 Session、回环地址服务及测试图片：

1. 馆长管理页面 200，名单仅含有效协作者信息，无密码/私人正文哨兵；协作者及配置为平台管理员的非馆长均 404；匿名跳转登录。
2. 移除前，成员 Museum 页面、私人 Memory API、私人图片均 200，照片上传 201。
3. 未登录 API 401；非馆长、移除自己、缺失/异站 Origin 均 403；未确认、字符串确认、伪造 actor、非法 JSON 均 400；不存在成员关系 404。
4. 合法移除 200，重复请求 200；数据库只有一条 `membership.remove`，actor 为馆长、objectId 为目标协作者，响应禁止缓存。
5. 使用原成员 Session 重新请求 Museum 页面、Memory、照片列表和私人图片均 404；旧页面继续编辑及新增上传均 404。
6. 原成员刷新账号页面后，Switcher 不再包含目标 Museum；自己的 Museum 照片接口仍 200。
7. 其他协作者仍能读取同一 Memory；馆长仍能读取原图片。馆长刷新成员管理页后只剩其他协作者，审计页显示“馆长移除协作者”。
8. 原记忆正文及已有照片数量保持不变。测试服务已停止，临时数据库、账号和图片已清理；未接触生产数据。

## 保留的边界与交付状态

- 移除的是协作者权限，不是封禁账号；不撤销有效邀请，也不改变公开记忆和独立分享规则。对方仍可作为普通访客访问公开内容；重新成为协作者仍需主动接受有效邀请。如不允许持旧邀请重新加入，可在既有邀请管理中撤销对应邀请。
- 未增加实时推送。已打开页面的旧选项可能留到刷新/重新切换，但不能继续获得私人内容或提交新操作；不能把界面缓存当成授权。
- 沿用现有上传恢复机制：保存中途被移除时，不提交照片记录，待恢复清理成功后释放文件及容量；不提前扣减仍占磁盘的用量。
