# Task12 J2 前置诊断

日期：2026-09-29。状态：前置诊断记录；用户随后回复“允许”，已授权通过接收转移管理多馆并保留接收方原馆。后续实现及验收见 `TASK12J2_VERIFICATION.md`。J1 及既有本地改动保留；未推送、未部署。

## 阻塞原因

执行文档同时规定：

1. B2：一个 User 最多拥有一个自己的 Museum。
2. E4 邀请接受前置：Own Museum exists。
3. J2：将 Museum Owner 转给当前 Collaborator。

正常流程中的接收协作者已经拥有自己的 Museum。若保留其原馆，再将目标馆的 `owner_id` 更新为该用户，会违反迁移 11 建立的 `museums_owner_unique` 唯一索引。删除或互换双方原馆没有用户授权，不能用来规避约束。

## 代码证据

- `src/data/migrations.ts` 迁移 11：拒绝多馆归同一 owner，并创建唯一索引。
- `src/data/museum-onboarding.ts`：已有 Own Museum 时拒绝创建第二个。
- `src/data/invite-acceptance.ts`：没有 Own Museum 时拒绝接受邀请。
- `src/data/museum-repository.ts` 的 `findMuseumByOwnerIdInDatabase`：按单一所有权返回一个馆。账号管理、默认内容范围、邀请和其他调用沿用此假设。

因此不能只删除唯一索引：否则现有单馆查询和账号管理可能选错馆，需要一起明确多馆选择和管理入口。

## 待决策

- 允许一个用户通过接收转移管理多馆，保留接收方原馆：先做必要的多馆管理适配，再完成 J2 的事务、确认、权限切换及旧馆长去留。这会调整 B2 的原有所有权规则。
- 保留一人一馆：仅无自有馆的有效协作者可以接收；正常邀请流程目前无法直接产生此条件，不能声称普通协作者转移已可用。需要另行明确如何合法产生该类接收人。

不自动删除任何馆，不自动互换双方所有权，不默认扩大数据模型。规则选择后再实施，后续仍只推进 J2，不进入 J3。
