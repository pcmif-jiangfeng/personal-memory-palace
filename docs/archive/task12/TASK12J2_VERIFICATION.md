# Task12 J2 — 馆长身份转移检测报告

日期：2026-09-29。范围：J2 及用户明确允许的必要多馆适配，不进入 J3；前序 G/H/I/J1 改动保留。未提交、推送或部署，正式站未改变。

## 结论与规则决定

已实现将馆长身份转移给当前有效、已验证邮箱的协作者，支持两步确认、事务提交、原馆长保留协作者身份或退出。接收方原有博物馆与内容保持不变。

执行文档 B2 的“一人最多拥有一个 Museum”与 E4/J2 冲突，详见 `TASK12J2_DIAGNOSIS.md`。用户回复“允许”后，决定允许通过接收转移管理多馆；不是删除、交换或合并双方原馆。每座 Museum 仍始终只有一个 Owner。

## 实现与行为

- 账号设置新增“转移馆长身份”，进入 `/account/museums/[id]/transfer`。接收方列表复用当前协作者查询，每页最多 25 人，只展示 ID、名称和邮箱，不含私人正文或密码。
- 第一步选择自己的去留并勾选理解后果；第二步明确显示目标馆、接收方名称/邮箱、自己的转移后身份，再点击最终确认。取消会撤销勾选。资料版本改变后，确认组件重新建立，避免沿用旧确认。
- `POST /api/museums/[id]/transfer` 要求同源、有效 User Session、当前 Owner 身份和严格的 `{ confirm: true, targetUserId, oldOwnerDisposition, version }`。拒绝未知字段、伪造 actor、模糊 ID、无确认及无效版本。
- 事务内重新核对当前 Owner、Museum active 状态、版本，以及目标是否仍为有效且邮箱已验证的协作者。馆长不能转给自己、无关用户或已被移除者；Platform Admin 身份不绕过馆长权限。
- `BEGIN IMMEDIATE` 内原子更新唯一的 `museums.owner_id`，不设空值、不引入并列 Owner。字段保留 NOT NULL 与 User 外键；提升目标时移除其协作者关系，原 Owner 按选择创建/恢复协作者关系或撤销已有关系。
- Museum 版本递增；原馆长旧页面不能继续修改馆长设置或管理邀请。即使所有权日后转回，最初的旧版本确认也不能再次生效。
- `museum.ownerTransfer` 审计记录实际 actor、Museum、前后 Owner ID 及原馆长去留；任一所有权、成员或审计写入失败都会回滚整笔转移。审计页仅新 Owner 可查看该馆完整记录。
- Museum ID、馆址、记忆、照片、配额、其他协作者及接收方原馆均不迁移、不覆盖；文件不复制、不重算存储。原 Owner 留任时拥有既有协作者内容权限，但失去 Owner 专属权限；退出时后续私人内容请求被拒绝。

## 必要多馆适配

- 新增迁移 22，删除单用户单馆的 Owner 唯一索引，并建立普通 Owner 查询索引；不修改既有迁移 11，也不改写内容行。迁移幂等验证覆盖既有单馆数据库升级及随后多馆状态再次初始化。
- Museum Switcher 的多个 Owner 选项各自进入 `/account?museumId=...`；资料、馆址、邀请创建/列表/撤销明确绑定页面所属 Museum。顶部导航、分页及返回链接保留对应馆。
- 多馆账户未指定目标就尝试修改馆长设置或邀请管理时返回 `MUSEUM_SELECTION_REQUIRED`，不能任意挑一座馆写入。明确指定失效或非本人管理的馆时直接拒绝，不回退到其他馆。
- 未选择馆的账号首页和既有默认内容查询按 `created_at,id` 稳定选择第一座自有馆，Switcher 使用相同排序。接收原本建立时间更早的馆可能改变无选择时的默认馆，但不会覆盖任何资料；通过切换器可分别管理。
- Onboarding 仍只允许尚无自有 Museum 的用户创建第一座馆；检查和插入现置于同一写事务，避免移除唯一索引后重复创建。没有额外开放“无限创建新馆”。
- 新共用馆长选择函数服务于资料、馆址和邀请三组真实消费者，复用既有 Museum 权限检查；无新增依赖。

### 真实本地 HTTP 验收

执行 `node --experimental-strip-types scripts/verify-owner-transfer.mjs`，只使用回环地址、合成账号/Session 和新建临时数据库：

1. 馆长转移页 200，并包含第一步确认入口和当前馆顶部导航；协作者和非馆长平台管理员 404，匿名跳转登录。响应不包含密码或私人内容哨兵。
2. 匿名转移 API 401；非馆长、缺失/外站 Origin 403；未确认、未知 actor 字段、非法去留 400；旧版本 409。
3. 合法转移 200、禁止缓存。原馆长重复请求被拒绝，不能再次转移；留任后成员页面与私人 Memory 仍可读取，但馆长设置、邀请页面及 API 不再允许。
4. 新馆长分别进入接收馆及原馆设置页，两者均 200，名称各自正确；Owner 的成员入口跳转到明确馆的设置地址。重复 `museumId` 参数 404，无目标的多馆设置写入 409。
5. 新馆长修改接收馆馆址后，原馆馆址保持不变；接收馆创建的邀请只出现在该馆列表，原馆列表仍为空。原馆长不能创建邀请。
6. 审计页新馆长可见转移记录，原馆长无法访问。另一笔转移验证退出分支：原 Owner 用原 Session 读取对应私人照片接口及成员页均 404，但自己的另一座馆仍可管理。
7. 两次转移各有一条审计，私人记忆正文保持不变，外键检查为空。服务已停止，本轮临时账号、数据库及构建数据已清理，未触及生产数据。
