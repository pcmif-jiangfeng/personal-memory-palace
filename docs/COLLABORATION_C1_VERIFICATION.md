# C1 指定邮箱邀请写入与撤销自检

日期：2026-10-03。结论：C1 服务完成；接受、邮件和页面仍由 C2/C3 实现，未开放生产协作。

## 改动与设计

- 新增 email-invite-schema.ts 与 email-invites.ts，迁移 31 创建 collaboration_invites。旧 invite_links 和历史记录不转换、不删除、不复用。
- 新邀请仅以指定标准化邮箱为目标，固定七天；ID 只定位记录，不是 bearer 凭证。这里没有认证 token，也没有非安全随机替代方案。
- 事务内检查最新馆长、账号验证和宫殿 active 状态，已有馆长/有效成员不能邀请；历史退出成员可收到新的邀请。
- 同馆同邮箱仅一份 pending 邀请；重复调用返回原记录，不续期、不重复审计。过期先关闭原 pending 再新增；撤销幂等，已接受不能用撤销替代移除。
- 查询每页 20 条并显式投影。邮箱仅在馆长邀请管理摘要中，不写入业务日志 diff；成员/访客管理请求拒绝。
- 新表同步纳入整馆删除白名单，保留删除测试对每张表、其他馆及账号完整性的断言，并新增数据夹具覆盖该表。

计划微调：旧 bearer 模型和新邮箱绑定的状态概念不同，采用独立表/服务，不在旧 useMode/maxUses 字段中模拟邮箱邀请；避免提前改 C2/C3 的接口和 UI。原旧接口当前仍关闭。后续入口必须调用新服务，不能恢复旧 token 接受服务。
