## 1. 产品定位

Personal Memory Palace 是一个个人数字人生博物馆。

用户通过照片和自己撰写的文字保存人生经历，并在未来通过浏览人生阶段或随机抽取 Memory，重新回忆过去。

它不是：

- 普通相册
- 日记软件
- 社交平台
- AI 日记
- 云盘

核心体验：

> 进入一座保存自己人生的现代数字博物馆，并重新遇见过去。

产品服务个人记忆与受邀共同记录；多人协作不意味着社区或社交平台。共同宫殿服务家庭、情侣、朋友等共同经历，私人宫殿继续服务个人经历。

---

## 2. 核心概念

### Stage

Stage 是用户自己定义的人生阶段。

例如：

- 大学本科
- 英国交换
- 摄影成长
- 科研探索

Stage 类似博物馆中的展厅、收藏册或人生章节。

系统不得预设标准人生阶段。

---

### Memory

Memory 是整个系统最重要的对象。

一个 Memory 可以：

- 只有 1 张照片；
- 包含多张照片；
- 表示一个瞬间；
- 表示一次旅行；
- 表示一段完整经历。

Memory 类似一场小型展览。

其中：

```text
Memory
├── Title
├── Story
├── Cover Image
├── Gallery Images
├── Stage（可选）
├── Related Memories（可选）
├── Later Notes
└── Visibility
```

照片是展品。

Story 是展览说明。

---

## 3. Story 原则

Story 必须是一整段自由纯文字。

不要强制拆成：

- 发生了什么
- 我的感受
- 未来寄语
- 固定模板字段

用户决定写什么。

V1 不做：

- Markdown
- 富文本
- Block Editor
- 图片文字混排

---

## 4. 创建 Memory 的核心流程

照片必须是创建 Memory 的入口。

正确流程：

```text
上传照片
→
照片整理台
→
选择若干照片
→
创建 Memory
→
填写标题
→
填写 Story
→
选择 Stage（可跳过）
→
关联 Memory（可跳过）
→
保存
```

不要以空白表单作为主要创建入口。

---

## 5. Photo Workspace

批量上传照片后，先进入照片整理台。

使用简单缩略图网格。

支持：

- 多选照片
- 取消选择
- 显示选择数量
- 使用选中照片创建 Memory

用户自己决定如何拆分照片。

不要：

- AI 自动分组
- 自动识别事件
- 自动分类
- 自动读取 EXIF

---

## 6. 图片原则

照片用于网页浏览，而不是专业摄影原片管理。

支持常见网页图片格式，例如：

- JPG
- JPEG
- PNG
- WebP

上传后：

```text
生成网页优化版本
+
用户可选择是否同时保留原始上传文件
```

V1 不需要支持 RAW。

不要读取或使用 EXIF。

---

## 7. 人生长廊

首页不是 Dashboard。

首页应该给用户：

> 进入自己人生博物馆的感觉。

整体视觉：

```text
Modern Museum
+
Warm Memory
+
Future Archive
```

关键词：

- 现代艺术馆
- 大量留白
- 安静
- 高级
- 温暖
- 少量未来科技感

不要：

- 赛博朋克
- 霓虹 HUD
- 大量数据卡片
- 后台管理系统视觉

---

## 8. Stage 的视觉

Stage 采用：

> 收藏册 / 书架式人生章节

而不是普通文件夹按钮。

鼠标 hover Stage 时：

约 3 张该 Stage 中的照片从收藏册后方展开。

动画应：

- 平滑
- 克制
- 高级
- 不夸张

---

## 9. 随机回忆：Time Gear

首页包含一个时间齿轮。

点击后：

```text
齿轮旋转
→
从当前宫殿中有权访问的有效 Memory 中完全随机选择一条
→
进入对应 Memory
```

必须完全随机。

不要使用：

- 浏览频率
- 重要程度
- 时间权重
- 推荐算法
- AI

未来可以增加“当年今日”，但不属于 V1。

---

## 10. Memory Exhibition

Memory 展示页是一场小型展览。

推荐结构：

```text
主视觉照片
标题
Story
照片画廊
Later Notes
Related Memories
Stage
```

Memory 不应被设计为“一张照片 + 一小段说明”。

---

## 11. Later Notes

Memory 创建后允许未来继续追加内容。

新增 Later Note 不得覆盖 Original Story；正常编辑 Story 是独立操作，不等于追加 Note。协作时只有 Note 作者可以改写该条 Note，馆长也不能改写他人的 Note。

结构应支持：

```text
Original Story
+
Later Notes
```

每条 Later Note 保存自己的创建时间。

协作作者、删除与恢复规则见协作规格；不因成员退出而删除其文字或作者归属。

目的是让未来的自己可以继续和过去对话。

---

## 12. Stage 与关联

Memory 创建时推荐选择 Stage，但不能强制。

必须允许：

```text
未归类 Memory
```

Memory 可以手动关联其他 Memory。

V1 不需要实现 Obsidian 式图谱页面。

---

## 13. 搜索

V1 只需要基础关键词搜索。

搜索：

```text
Memory.title
Memory.story
```

不做：

- AI 搜索
- 语义搜索
- 人物搜索
- 地点搜索
- 高级筛选

---

## 14. 删除

照片、Memory、Stage 的删除先进入回收站。馆长与协作者可以移入、恢复；永久删除与清空回收站仅限馆长。Later Note 的例外权限见协作规格。

共同宫殿整体删除进入 30×24 小时待删除期，成员与外部分享停止访问，成员、邀请、分享管理及转让冻结；馆长只能查看状态并在截止前撤销。期满不可撤销，后台执行永久删除，失败重试且不恢复访问。私人宫殿整体删除与账号注销本阶段不开放，不得套用共同宫殿规则。

不得直接永久删除 Memory 或 Stage。

流程：

```text
删除
→
回收站
→
恢复 / 永久删除
```

---

## 15. 分享

分享与协作是独立权限路径。只有馆长可创建、修改、关闭外部分享；分享链接不授予成员身份或编辑权。已分享内容更新后，分享展示同步更新，界面须明确提示。

网站默认是私人博物馆。

Owner：

```text
完整内容
+
编辑能力
```

Visitor：

```text
同一套博物馆 UI
+
仅允许分享的 Memory
+
只读
```

分享出去后不做单独的“公共展示页”。

朋友看到的应该仍然是同一座人生博物馆，只是内容经过筛选。

分享支持：

- 有链接即可访问
- 链接 + 密码

不需要自动过期。

---

## 16. 账号、宫殿与成员

允许公开注册，登录统一使用邮箱和密码；未验证邮箱账号只能使用验证流程，不能进入正式私人或协作业务。

每个账号拥有一个私人宫殿，同时可以创建或加入共同宫殿，也可以受邀协助他人的私人宫殿。私人宫殿与共同宫殿各自只有一个馆长。

- 私人宫殿馆长始终是原账号，不可转让。
- 共同宫殿可转让给现有协作者，须对方接受；原馆长随后成为协作者。
- 馆长与协作者可以查看该宫殿全部业务内容，包括加入前的内容，但不能因此访问成员的其他宫殿、账号凭证或私人账号信息。
- 每次读写、搜索、统计和随机回忆都必须限定目标宫殿并验证权限。
- 宫殿之间数据不自动互通，本阶段不提供跨宫殿复制或移动。
- 邀请绑定指定邮箱，完成注册、邮箱验证并主动接受后才获得权限。
- 邀请与共同宫殿馆长转让申请均自创建起 7 天有效，细则见协作规格。
- 本阶段不新增共同宫殿创建数、加入数与成员数的产品限制，不承诺无限容量；存储仍受馆长账号配额限制。

馆长的私人宫殿与其管理的共同宫殿共用账号配额，协作者上传计入目标馆长。保留的优化版、原始文件、回收站和待删除文件计入占用，同一实体文件不重复计量；真实删除后释放。共同宫殿转让须再次校验接任账号配额，成功后整体变更该馆配额承担者。实现前核对旧计量口径并明确迁移影响。

不做社区、好友、关注、私信、评论或点赞。Later Note 是宫殿内的记忆追加，不是公开评论系统。

## 17. 响应式

Desktop 和 Mobile 都必须可用。

Desktop 重点：

- 批量上传
- 整理照片
- 创建 Memory
- 管理 Stage
- 编辑关联

Mobile 重点：

- 浏览
- 随机回忆
- 阅读 Memory
- 简单编辑
- 分享

产品不是实时记录工具。

核心流程是：

```text
经历发生
→
照片产生
→
之后整理
→
形成 Memory
```

---

## 18. 公网

V1 最终需要部署到公网。

不能只支持 localhost。

需要：

- 电脑访问
- 手机访问
- 分享链接访问
- 数据持久化

---

## 19. Owner 安全

由于公网部署包含编辑能力：

编辑入口必须受到最基本保护。

统一复用 User、服务端 Session 与邮箱验证码体系，不接受旧馆长密码作为特殊身份。密码至少 8 位，哈希存储；未验证账号保持受限会话。

权限必须在服务端验证，不能只隐藏按钮。授权来源只能是目标宫殿的馆长身份、有效协作成员身份或有效只读分享凭证；没有授权的用户默认不能访问。

---

## 20. Demo 数据

第一次启动不能只有空白页面。

此要求适用于独立 Demo 展示，不适用于正式新账号：新账号进入自己的空白私人宫殿，不继承馆长或 Demo 数据。

项目中提供少量独立 Demo 数据，用于展示：

- Stage
- Memory
- 多图 Memory
- Related Memory
- Time Gear
- Stage hover

Demo 数据必须与真实用户数据隔离，并容易关闭或清除。

---

## 21. 视觉主题

V1 只维护一套主题。

不做：

- Dark Mode
- Theme Editor
- 多主题

集中精力把一套视觉做完整。

---

## 22. 国际化

V1 UI 使用中文。

但不要把所有中文文案散落硬编码。

为未来增加英文预留基本文案组织结构。

V1 不需要真正提供语言切换。

---

## 23. 技术选型原则

具体技术栈由开发者根据项目现状选择。

优先级：

1. V1 开发效率
2. 公网部署简单
3. 图片上传方便
4. 数据结构清晰
5. 未来可继续发展
6. 成本低
7. 代码易读
8. 不过度工程

不要因为“未来可能很大”而提前构建复杂系统。

---

## 24. 架构原则

虽然 V1 是原型，但必须是可演化原型。

至少保持：

```text
UI / Components
Domain Logic
Data Access
Image Storage
Database
```

之间基本分离。

避免：

- 所有代码写在一个文件
- UI 直接操作数据库
- 分享逻辑散落各页面
- 图片处理逻辑高度耦合
