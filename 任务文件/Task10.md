# Personal Memory Palace — Task 10 问题修复与体验增强

> 文档用途：本文件是可直接交给 Codex 的分阶段实施规范。  
> 核心纪律：**Task 10A–10I 严禁一次性全部执行；一次只实施、验证和验收一个 Task。**  
> 完成判定：Codex 自测通过不等于任务完成；只有用户人工验收通过并建立 Git checkpoint 后，才可进入下一 Task。

---

## 1. 背景与目标

Personal Memory Palace 已从概念原型进入长期真实使用阶段。本轮工作同时涉及照片查看、Stage 生命周期、照片物理删除、封面选择、上传管线、照片工作台、人生长廊浏览、展品元数据、导航反馈和随机回忆。它们虽同属 Task 10，但属于不同的业务边界和数据生命周期，不能作为一次大改动交付。

本轮目标是：

1. 修复当前明确的行为缺陷；
2. 建立统一、可解释、可验证的照片生命周期；
3. 在不破坏现有数据和主要行为的前提下改善照片工作流；
4. 保持产品的 `Modern Museum + Warm Memory` 视觉语言；
5. 以小步、可回滚、逐项人工验收的方式降低回归风险。

### 1.1 总体产品原则

- Memory 是核心叙事对象；Photo 是可复用的物理资产；一张 Photo 可被多个 Memory 引用。
- Stage 是组织 Memory 的分类容器；删除 Stage 不等于删除 Memory。
- 图片删除必须引用安全；只有没有任何业务引用时才允许物理删除。
- 用户上传的照片不会因“尚未整理”而被系统自动删除。
- 新上传图片只保留客户端压缩后的 Web 优化版本，不新增原图留存；历史原图不得因此被擅自清理。
- Workspace 是创建或编辑 Memory 时的照片工作台，不是简单的“垃圾箱”或仅包含未整理照片的池子。
- 交互改进优先解决根因，不以局部样式补丁掩盖数据或状态问题。

## 2. 强制执行纪律：禁止一次执行全部任务

### 2.1 单任务门禁

必须严格执行以下循环：

```text
读取永久上下文与当前 Task
→ 调查当前实现与基线
→ 只实施当前 Task
→ Codex 自测与静态检查
→ Codex 提交完成报告和人工验收路径
→ 停止
→ 用户人工验收
→ 修复当前 Task（如未通过）
→ 用户确认通过
→ Git commit / checkpoint
→ 才可进入下一 Task
```

### 2.2 明确禁止

- 禁止在一次请求中实现 Task 10A–10I 全部内容。
- 禁止在当前 Task 中“顺便”实现后续 Task。
- 禁止因未来可能需要而提前进行大范围重构、抽象或数据迁移。
- 当前 Task 未通过人工验收时，只能修复当前 Task，不得推进下一项。
- 尤其禁止把 10C、10E、10F 合并实施：三者分别处理删除、上传和照片组织生命周期，合并会显著扩大数据回归面。
- 除非当前 Task 的正确实现确实依赖，否则不得改变现有分享、认证、权限、Memory、Stage、图片展示或其他无关功能。

### 2.3 每项任务的停止要求

下文每个 Task 均有独立的“停止点”。完成代码、迁移、测试、报告后，Codex 必须停止并等待用户人工验收。不得自动开始下一 Task，也不得把“已计划”误报为“已完成”。

## 3. Task 10A — 修正 Memory 照片查看器起始图片

### 3.1 目标

用户点击 Memory 展览中的任意展品照片后，全屏查看器必须从**实际点击的照片**打开，而不是固定从 Memory Cover 开始。

### 3.2 实现规则

- 查看器的 `initialIndex` 或等价起始定位必须由被点击照片在当前可浏览照片集合中的稳定身份/索引计算。
- Memory Cover 若属于该 Memory 的图片集合，仍正常参与浏览，不得被特殊排除。
- 左右切换顺序必须与展览中定义的照片顺序一致。
- 优先传递稳定的 Photo 或关系记录 ID，再在查看器数据源中解析索引，避免仅靠易变化的数组位置造成错位。
- 不修改与本缺陷无关的缩放、拖拽、键盘切换、触摸手势或图片排序逻辑。

示例：

```text
图片顺序：A（同时是 Cover）→ B → C → D
点击 C：查看器首次显示 C
随后向左：B
随后向右：C，再向右：D
```

### 3.3 边界情况

- 点击第一张、中间一张、最后一张。
- Cover 位于第一张、非第一张，或 Cover 未设置。
- 数据刷新或异步加载后，点击照片仍能定位正确。
- 某张照片在打开前已被合法移除时，应安全降级，不得崩溃；可关闭查看器或定位到仍存在的最近有效项。
- Desktop 与 Mobile 行为一致。

### 3.4 验收标准

- [ ] 点击第一张时从第一张打开。
- [ ] 点击中间照片时从对应照片打开。
- [ ] 点击最后一张时从最后一张打开。
- [ ] Cover 不会覆盖实际点击项的起始索引。
- [ ] 左右浏览顺序正确且无重复/跳图。
- [ ] 手机端点击结果一致。
- [ ] 现有缩放、拖拽、关闭等功能无回归。

### 3.5 停止点

完成针对性测试和完成报告后停止，等待用户人工验收。不得开始 Task 10B。

## 4. Task 10B — Stage 删除入口与删除语义

### 4.1 目标

让 Stage 删除入口清晰可发现，并把删除语义固定为：**删除 Stage，保留其所有 Memory，并将这些 Memory 设为未归类。**

### 4.2 实现规则

- 首页人生长廊的每张 Stage 卡片右上角提供 `···` 更多菜单，至少包含“编辑 Stage”和“删除 Stage”。
- Stage View 内提供清晰的“删除 Stage”入口。
- 两个入口必须复用同一个服务/命令和确认流程，不得复制两套语义。
- 删除前显示明确确认，说明 Stage 会消失，但其中 Memory 会保留并变为“未归类”。
- 删除操作应具备事务性：Stage 删除与 Memory 解除归类必须全部成功或全部回滚。
- 删除后刷新相关缓存/查询，使首页、Stage View、Memory 列表和筛选状态立即一致。

删除后必须保持：

- Memory 记录仍存在；
- Memory 不进入回收站，不被软删除或永久删除；
- Story、照片关系、封面和 Related Memory 不变；
- `stageId` 或等价归类关系变为未归类状态；
- 原 Stage 不再出现在导航、筛选和封面选择等位置。

### 4.3 边界情况

- 删除空 Stage。
- 删除仅含一个 Memory 的 Stage。
- 删除含多个 Memory 的 Stage。
- 某 Memory 本来就允许无 Stage，迁移后页面必须正常显示。
- 删除过程中出现数据库错误时，不得产生“Stage 已删但 Memory 仍指向不存在 Stage”的半完成状态。
- 重复提交、慢网络和双击不得导致异常或重复提示。
- 用户无权限时，服务端必须拒绝；隐藏按钮不能替代服务端授权。

### 4.4 验收标准

以以下数据为例：

```text
Stage A
├── Memory 1
├── Memory 2
└── Memory 3
```

- [ ] 首页卡片 `···` 可删除 Stage A。
- [ ] Stage View 可删除 Stage A。
- [ ] 两处确认文案和最终行为一致。
- [ ] 删除后 Stage A 不存在。
- [ ] Memory 1、2、3 均存在且显示为“未归类”。
- [ ] 三个 Memory 的 Story、图片、封面和关联关系保持不变。
- [ ] 空 Stage 删除正常。
- [ ] 失败场景无悬空外键和部分提交。

### 4.5 停止点

完成针对性测试和完成报告后停止，等待用户人工验收。不得开始 Task 10C。

## 5. Task 10C — 照片引用安全与真正物理删除

### 5.1 目标

建立唯一、统一的照片删除生命周期，解决数据库记录已删除但 Stage Cover Selector 等位置仍出现“幽灵照片”的问题，并确保有引用照片不能被物理删除。

### 5.2 实现规则

物理删除前必须由服务端集中检查当前用户范围内的全部业务引用，至少包括：

- Memory–Photo 关系；
- Memory Cover；
- Stage Cover；
- 项目中已存在的其他图片关联、分享或派生引用。

有任何引用时：

- 阻止数据库记录与物理文件删除；
- 返回结构化、可展示的引用信息；
- UI 说明为什么不能删除，并尽可能列出引用对象，例如 Memory 标题和 Stage 标题。

无任何引用时：

- 允许删除图片数据库记录及系统实际保存的 Web 优化物理文件；
- 数据库状态与文件删除必须按现有存储能力设计成一致、可重试的流程；不得静默留下永久孤儿文件或“记录存在但文件消失”的状态；
- 删除后统一失效相关缓存和选择器数据。

新规则只处理系统实际保存的优化图。**不得因为本 Task 或后续“不再保留原图”的规则自动删除历史原图。** 历史资产若需要清理，必须另立任务和迁移方案。

### 5.3 边界情况

- 同一 Photo 被多个 Memory 复用，只要任一引用存在就不得物理删除。
- Photo 同时是 Memory Cover 和 Stage Cover，需展示全部或足以说明阻塞的引用。
- 已解除 Memory 关系但仍是 Cover 时不得删除。
- 物理文件已丢失但记录存在时，删除应可幂等完成并记录可诊断信息。
- 数据库记录已不存在的重复请求应安全处理，不得误删其他文件。
- 物理路径必须来自可信存储键，禁止接受客户端任意文件路径。
- 并发情况下，引用检查与删除之间不得让新引用写入形成竞态；使用事务、锁、约束或等价机制守住不变量。

### 5.4 删除后全局一致性

成功删除的照片必须从以下所有位置消失：

- Workspace；
- Existing Photo Library；
- Memory Photo Picker；
- Stage Cover Selector；
- 其他图片选择器和缓存列表。

### 5.5 验收标准

- [ ] 无引用 Photo：删除成功，数据库记录消失，物理优化图不存在。
- [ ] Memory 引用存在：删除被阻止并显示引用原因。
- [ ] Memory Cover 引用存在：删除被阻止。
- [ ] Stage Cover 引用存在：删除被阻止。
- [ ] 多 Memory 复用：解除部分引用后仍不能删除。
- [ ] 解除全部引用后再次删除成功。
- [ ] 成功删除后所有选择器均无幽灵照片。
- [ ] 重复删除和异常重试安全。

### 5.6 停止点

完成迁移（如需）、针对性测试和完成报告后停止，等待用户人工验收。不得开始 Task 10D。

## 6. Task 10D — 重新设计 Stage Cover Selector

### 6.1 目标

把当前生硬、依赖文件名且层级松散的 Stage Cover 选择体验重构为完整的 `Stage Cover Selector Card`，而不是只调整 margin。

### 6.2 实现规则

组件至少包含：

1. 候选图片区域；
2. 可辨识的图片缩略图；
3. 明显的当前选中状态；
4. 较大的当前封面实时预览；
5. 独立、低优先级但清晰的状态/说明区域。

具体要求：

- 用户无需记住文件名，仅凭视觉即可选择封面。
- 选择候选图后，大预览立即更新；最终保存仍遵循现有编辑提交语义。
- 当前项不能只靠颜色表示，可结合边框、选中图标、文字或 `aria-selected` 等状态。
- 候选集只能来自当前用户可访问、未删除且允许作为 Stage Cover 的照片。
- 不得重新上传或复制图片来设置封面，只建立引用。
- 辅助文案（如“封面已从上传的照片中选择”）与控件保持合理距离并降低视觉权重。
- 保持 `Modern Museum + Warm Memory`，避免后台管理系统式密集表单。

### 6.3 边界情况

- 没有候选照片时提供清楚空状态和下一步入口。
- 当前封面后来失效时不渲染破图，应显示可恢复空状态。
- 候选很多时支持高效滚动/分页/渐进加载，不一次解码全部大图。
- 竖图、横图、超宽图和不同长宽比均需稳定裁切预览，不扭曲。
- 键盘可定位和选择候选项，焦点清晰。
- 小屏幕不应让大预览挤压候选区至不可操作。

### 6.4 验收标准

- [ ] 不看文件名也能完成封面选择。
- [ ] 当前封面有大预览。
- [ ] 当前候选项状态清晰且不只依赖颜色。
- [ ] 选择后预览即时、准确更新。
- [ ] 无候选图时有明确空状态。
- [ ] 大量候选图和不同长宽比布局稳定。
- [ ] Mobile 与键盘操作可用。
- [ ] 已删除照片不再出现。

### 6.5 停止点

完成视觉和交互验收路径说明后停止，等待用户人工验收。不得开始 Task 10E。

## 7. Task 10E — 新图片上传管线与全局任务进度

### 7.1 目标

建立客户端压缩、逐文件容错、跨页面持续存在、可展开查看详情且可取消的上传任务管线。

### 7.2 新图片存储规则

- 移除“是否保留原图”选项。
- 新图片流程固定为：

```text
本地原始文件
→ 浏览器读取与校验
→ 客户端压缩/转换
→ 上传 Web 优化版本
→ 服务端只保存该优化版本
```

- 不新增第二份原图保存。
- 不删除或迁移既有历史原图；旧数据必须继续兼容。
- 服务端仍需验证真实 MIME、尺寸和可接受文件类型，不能信任扩展名或客户端声明。

### 7.3 大文件与压缩规则

- 不能只因本地原图大于 20 MB 就直接拒绝。
- 应先尝试在浏览器端读取和压缩，再针对**真正要上传的优化文件**执行上传限制判断。
- 浏览器解码、内存或压缩失败时，只标记该文件失败，不拖垮整批。
- 压缩采用“画质/存储平衡”目标：正常全屏清晰、轻度放大可用、体积明显低于原图，但不追求原图级极端放大细节。
- 需求层不硬编码单一 WebP quality。Codex 应结合现有链路、浏览器支持和样本测试选择尺寸、格式与质量参数，并在报告中说明依据和实际值。
- 保留正确方向，处理 EXIF orientation；不得把照片压成错误旋转方向。

### 7.4 逐文件弹性处理

批量任务按文件独立记录状态，至少包含：

- 等待处理；
- 正在压缩；
- 正在上传；
- 成功；
- 失败；
- 已取消。

例如 20 张中 17 张成功、3 张失败时：

- 17 张正常进入系统；
- 3 张保留失败状态及具体原因；
- 不得整批回滚或只显示模糊的“上传失败”；
- 最终汇总显示成功、失败、取消数量。

### 7.5 全局悬浮进度卡

- 处理期间在右下角显示 `Global Upload Task Card`。
- 卡片展示整体进度和成功/失败/取消统计，例如 `8 / 20`。
- 从 Workspace 导航到首页、Stage、Memory 或其他前端路由时，卡片仍存在且任务继续。
- 状态必须放在路由之上的应用级任务管理边界中；不能依赖某个页面组件存活。
- 页面真正刷新/关闭时，至少要给出符合现有产品能力的安全行为；若不实现跨刷新续传，必须避免把未完成项误标为成功，并在报告中明确限制。
- 卡片可展开查看每张图片的当前状态和失败原因。
- 已全部结束的任务允许用户主动关闭；进行中的任务不可因关闭视觉卡片而悄悄中止。

### 7.6 取消规则

- 支持取消单张和取消整批。
- 不实现暂停/恢复。
- 已成功上传的照片在随后取消整批时保留，不自动删除。
- 尚未开始的项立即标记已取消。
- 正在压缩/上传且能安全中止的项应使用取消信号终止；不得在取消后又被迟到响应标成成功。
- 被取消且未完成上传的图片不得进入 Workspace。
- 若服务端已完成持久化而客户端才收到取消，应以真实持久化结果为准，并清楚呈现，避免产生不可见孤儿资产。

### 7.7 边界情况

- 单张正常照片、20 张混合照片、重复文件名、零字节或损坏文件、不支持格式。
- 大于 20 MB 的本地原图压缩成功与压缩失败。
- 快速连续启动多个批次时，任务身份和统计不能串批。
- 弱网、超时、服务端拒绝、鉴权过期。
- 导航期间组件卸载，任务不丢失。
- 单张取消与整批取消同时触发。
- Mobile 内存有限，应控制并发和解码峰值，避免同时展开大量原图。

### 7.8 验收标准

- [ ] 单张正常上传成功。
- [ ] 20 张批量任务可见逐文件进度。
- [ ] 混合成功/失败时成功项保留，失败项有具体原因。
- [ ] 本地原图 >20 MB 时先压缩，不按原始体积直接拒绝。
- [ ] 新上传图片只保存优化版本，不新增原图副本。
- [ ] 切换页面后卡片和任务持续存在。
- [ ] 展开卡片可查看每张状态。
- [ ] 可取消单张。
- [ ] 可取消整批，且已成功项保留。
- [ ] 不存在暂停/恢复入口。
- [ ] Mobile 可完成上传且不明显冻结。
- [ ] 报告中记录实际压缩参数、并发策略与跨刷新限制。

### 7.9 停止点

完成针对性测试、样本验证和完成报告后停止，等待用户人工验收。不得开始 Task 10F。

## 8. Task 10F — Workspace + Existing Photo Library

### 8.1 目标与定义

Workspace 是**创建/编辑 Memory 时统一选择照片的工作台**。它同时提供两个来源：

```text
来源 A：本次/最近上传、尚在整理流程中的照片
来源 B：Existing Photo Library（已有照片库）
```

用户可以只选一个来源，也可跨来源混合多选，共同组成一个 Memory。

### 8.2 Existing Photo Library 的收录规则

照片库使用同一网格，包含两类照片：

1. **已用于 Memory**：只要 Photo 被任意 Memory 使用过，就自动进入照片库；
2. **未用于 Memory**：用户主动归档到照片库、当前未被任何 Memory 使用的照片。

必须明确区分“照片库成员资格”和“当前引用数”：

- Photo 曾用于 Memory 后自动成为照片库成员；
- 用户可在上传后主动归档，使其在零 Memory 引用时成为照片库成员；
- Photo 与某个 Memory 解除关系后，不能因引用数变为零就自动物理删除；其照片库状态按既定归档/历史使用语义保留，除非用户主动删除且引用检查通过。

### 8.3 工作台交互

- 创建或编辑 Memory 时进入统一照片选择器。
- 可在“本次上传”和“已有照片库”之间切换，保留当前选择状态。
- 支持跨来源多选、取消选择，并在提交前清楚展示已选数量。
- 提交 Memory 时只创建关系，不复制物理文件。
- 同一 Photo 可以同时属于 Memory A、B、C；每个关系独立。
- 重复选择同一 Photo 时必须去重，不能给同一 Memory 创建重复关系。

### 8.4 状态角标与筛选

已有照片库保持**单一图片网格**，每张图显示清晰状态角标：

- `已用于 Memory`
- `未用于 Memory`

并至少提供：

- 全部 / 已用于 Memory / 未用于 Memory 的状态筛选；
- 按 Memory 标题搜索相关照片；
- 按 Stage 筛选相关 Memory 使用过的照片。

搜索和筛选语义：

- 一张 Photo 被多个 Memory 使用时，只要任一关联 Memory 标题匹配就出现一次；
- Stage 筛选基于 Photo 所关联 Memory 的 Stage；Photo 同时跨多个 Stage 时在任一对应筛选中出现一次；
- 未用于 Memory 的照片在具体 Memory 标题或 Stage 筛选下通常无匹配，但仍可在状态筛选中找到；
- 搜索、Stage 和状态筛选组合时，应采用可预测的交集语义，并提供清除筛选入口。

### 8.5 未处理照片与删除

- 新上传 Photo 即使既未加入 Memory，也未主动归档到 Existing Photo Library，仍必须保留。
- 不因离开 Workspace、关闭弹窗、超时或后台任务结束而自动删除。
- 删除只能由用户主动触发。
- Workspace 中的删除必须复用 Task 10C 的统一引用检查与物理删除逻辑；不得另写宽松删除接口。

### 8.6 边界情况

- 同一 Photo 被多个 Memory 复用，网格只展示一个物理资产。
- Photo 关联多个 Stage 下的 Memory，Stage 筛选结果去重。
- Memory 标题修改后搜索索引/查询结果更新。
- Stage 删除后相关 Memory 变为未归类；对应 Photo 不再匹配已删除 Stage，但仍保留。
- 从当前 Memory 移除 Photo 不影响其他 Memory 的引用。
- 大量照片时使用缩略图、分页/虚拟化或渐进加载，避免全量大图解码。
- 多选期间筛选切换不得悄悄清空用户选择；如确需清空必须明确提示。

### 8.7 验收标准

- [ ] 新上传照片可用于创建 Memory。
- [ ] Memory 使用过的照片自动进入 Existing Photo Library。
- [ ] 未用于 Memory 的照片可手动归档到照片库。
- [ ] 两类照片在同一网格中以不同角标显示。
- [ ] 状态筛选正确。
- [ ] 可按 Memory 标题搜索。
- [ ] 可按 Stage 筛选。
- [ ] 可混合选择新上传与图库照片。
- [ ] 同一 Photo 可加入第二、第三个 Memory。
- [ ] 复用不会创建重复物理文件。
- [ ] 同一筛选结果不会因多重关系重复展示。
- [ ] 未处理照片不会自动消失。
- [ ] 主动删除遵守 Task 10C 引用安全规则。

### 8.8 停止点

完成数据、查询和交互测试及完成报告后停止，等待用户人工验收。不得开始 Task 10G。

## 9. Task 10G — 人生长廊 Stage 横向浏览

### 9.1 目标

Stage 数量增加时保持卡片尺寸和视觉节奏稳定，通过同一横向滚动容器支持箭头、鼠标/触控板和触屏浏览。

### 9.2 实现规则

- Stage 卡片使用稳定的固定宽度和固定高度；数量增加时不得压缩卡片。
- Stage 区域采用横向滚动容器。
- 左右箭头每次精确移动**一个 Stage 卡片单位**，单位应包含卡片宽度和实际间距。
- 箭头与自然滚动必须控制同一个容器。
- 支持鼠标/触控板横向滚动、触屏滑动和常规滚动。
- 使用合适的 scroll snap，使停止后尽可能完整对齐卡片。
- 到最左端时左箭头禁用或隐藏；到最右端时右箭头禁用或隐藏。
- 不能只用硬编码像素推算位置；需兼容响应式间距、缩放和滚动容器尺寸。

### 9.3 边界情况

- Stage 数量不足一屏时不显示无意义的箭头或正确保持禁用。
- 3、5、10、20 个 Stage。
- 窗口缩放、设备方向切换后边界判断更新。
- 快速连续点击箭头，不跳过或累积到错误位置。
- 用户自然滚动到中间后，再点击箭头应从当前最近卡片移动一个单位。
- 键盘和辅助技术可访问箭头，按钮有可理解名称。
- 尊重 `prefers-reduced-motion`，减少或取消非必要平滑动画。

### 9.4 验收标准

- [ ] 3、5、10、20 个 Stage 下卡片尺寸一致，不被压缩。
- [ ] 每次箭头点击移动一个卡片单位。
- [ ] 自然滚动和箭头同步。
- [ ] 停止后主要展示位置没有难看的半张卡片。
- [ ] 两端按钮状态准确。
- [ ] Desktop、触控板和 Mobile 触摸操作正常。
- [ ] 缩放和方向切换后仍正确。

### 9.5 停止点

完成多数量、多视口测试和完成报告后停止，等待用户人工验收。不得开始 Task 10H。

## 10. Task 10H — 单个展品标题与说明

### 10.1 目标

Memory 保留整体 Story，同时允许其中每张展品照片拥有独立的可选标题与说明。

### 10.2 数据归属与实现规则

字段必须存储在 **Memory–Photo 关系** 上，而不是 Photo 物理资产本身。建议在现有关系模型（如 `MemoryImage`）中增加可空字段：

```text
exhibitTitle?: string | null
exhibitDescription?: string | null
```

字段名可依项目惯例调整，但语义必须保持：

- 同一物理 Photo 在 Memory A 中可有一套标题/说明；
- 在 Memory B 中可有另一套；
- 修改 A 的展品信息不能影响 B，也不能修改 Photo 全局元数据。

迁移必须兼容既有关系记录，默认无标题、无说明。

### 10.3 编辑交互

禁止在 Memory Editor 中同时展开所有图片的标题和说明字段。正确流程：

```text
选择某张照片
→ 打开该展品设置
→ 编辑标题与说明
→ 保存
```

只有当前正在编辑的展品显示输入控件。需清楚标识正在编辑哪张图，并防止切换图片时静默丢失未保存内容。

### 10.4 展示规则

- Memory Exhibition：有标题或说明时，在图片附近展示已有内容；没有的字段不显示。
- Fullscreen Viewer：放大后完整显示该关系记录的 Exhibit Title 和 Exhibit Description。
- 标题和说明都为空时，不渲染空区域、占位符或多余间距。
- 只有标题时只显示标题；只有说明时只显示说明。
- 文本按纯文本安全渲染或经过项目统一富文本清理，不允许未清理 HTML 注入。

### 10.5 边界情况

- 无说明、仅标题、仅说明、两者都有。
- 添加、修改、清空字段。
- 同一 Photo 在两个 Memory 中使用不同文案。
- 删除 Memory–Photo 关系时只删除该关系上的展品元数据，不影响物理 Photo 和其他关系。
- 长标题、长说明、多语言、换行和移动端展示。
- 保存失败时保留可恢复编辑状态并显示错误。
- Viewer 起始照片和切换行为继续满足 Task 10A。

### 10.6 验收标准

- [ ] 既有数据迁移后正常，字段默认为空。
- [ ] 每次只编辑当前选中展品，不产生臃肿表单。
- [ ] 无说明、仅标题、仅说明、两者都有均正确展示。
- [ ] 可修改并清空标题/说明。
- [ ] Fullscreen Viewer 展示完整文案。
- [ ] 空字段不占空间。
- [ ] 同一 Photo 在不同 Memory 的展品文案彼此独立。
- [ ] Mobile 长文本布局可用。

### 10.7 停止点

完成迁移、关系级数据测试和完成报告后停止，等待用户人工验收。不得开始 Task 10I。

## 11. Task 10I — 顶部导航反馈与 Time Gear 空状态

本 Task 包含两个轻量的最终收尾项，但仍只在前序任务全部验收后执行。

### 11.1 A：加强顶部导航状态

#### 目标

让用户无需仔细辨认即可知道“哪些入口可点击”和“当前在哪个功能”，同时保持 Modern Museum 视觉气质。

#### 实现规则

- 综合使用清晰文字层级、图标、hover、active、focus、背景/描边/指示条。
- 当前状态不能只依靠低对比度色差或颜色单一线索。
- 使用路由或现有导航状态作为唯一可信来源，刷新和深链进入时激活项正确。
- 可点击区域、键盘焦点和语义元素符合无障碍要求。
- 不做成后台系统式的大块高饱和按钮。

#### 边界情况

- 首页、Stage、Memory、Workspace 等直接深链进入。
- 浏览器前进/后退后激活状态更新。
- 窄屏导航折叠后仍可辨识当前项。
- hover、focus、active 状态不得相互覆盖到无法识别。

#### 验收标准

- [ ] 可点击入口一眼可辨。
- [ ] 当前功能状态清楚。
- [ ] 刷新、深链、前进/后退后状态正确。
- [ ] 键盘焦点明显。
- [ ] 视觉仍符合 Modern Museum。

### 11.2 B：Time Gear 随机与仪式感空状态

#### 数据规则

- Time Gear 随机对象是 **Memory**，不是 Photo，也不是“至少含一张照片的 Memory”。
- 候选集合为当前用户有权访问且业务状态有效的全部 Memory。
- 没有照片的纯文字 Memory 仍可被随机到，并正常进入其无图展览页。
- 只有系统中不存在任何有效 Memory 时，才进入空状态。

#### 交互规则

即使没有任何 Memory，Time Gear 仍可点击：

```text
点击
→ 短暂旋转/仪式动画
→ 确认无有效 Memory
→ 显示具有仪式感的空状态
→ 提供“创建第一段 Memory”等自然入口
```

文案可根据现有语言优化，例如“这里还没有可以遇见的过去。”

禁止：

- 无响应或抛出错误；
- 把齿轮置灰为完全不可点击；
- 因为 Memory 没有照片就排除它；
- 把“有 Memory 但全都无图”误判为空状态。

#### 边界情况

- 0 个有效 Memory。
- 只有一个无图 Memory。
- 只有多个无图 Memory。
- 有图和无图 Memory 混合。
- 已删除、无权限或非有效状态 Memory 不进入候选。
- 快速重复点击不应并发导航或产生多次结果。
- 动画尊重 `prefers-reduced-motion`。

#### 验收标准

- [ ] 0 个 Memory 时可点击并出现仪式感空状态与创建入口。
- [ ] 只有无图 Memory 时仍可随机到并正常打开。
- [ ] 混合数据时无图 Memory 不被过滤。
- [ ] 无效/无权限 Memory 不参与。
- [ ] 快速重复点击安全。
- [ ] 减少动态效果偏好生效。

### 11.3 停止点

完成所有测试和最终完成报告后停止，等待用户最终人工验收。不得自行扩展新的 Task。

## 12. 全局照片生命周期规则

以下是不因单个页面而变化的全局不变量：

```text
本地选择文件
→ 客户端校验与压缩
→ 仅上传 Web 优化图
→ 生成一个 Photo 物理资产记录
→ 保留在系统中，直到用户主动请求删除
```

Photo 后续可处于或同时参与以下状态：

```text
尚未处理/决定
主动归档到 Existing Photo Library（未用于 Memory）
被一个或多个 Memory 引用（已用于 Memory，自动进入 Library）
被引用为 Memory Cover
被引用为 Stage Cover
```

### 12.1 必须保持的关系

- 一个 Photo 物理资产可对应多个 Memory–Photo 关系。
- 复用 Photo 不复制物理文件。
- Exhibit Title/Description 属于 Memory–Photo 关系，而不是 Photo。
- “未用于 Memory/已用于 Memory”由当前 Memory 引用状态得出；照片库成员资格还可由用户主动归档产生。
- 任何引用存在时，物理删除必须被阻止。
- 无引用并不等于自动删除；仍需用户主动确认。
- 删除入口无论来自 Workspace、Library 或其他页面，都必须调用同一套服务端引用检查与删除逻辑。

### 12.2 不得发生

- 因离开 Workspace 自动清理未处理照片。
- 为同一照片加入第二个 Memory 而生成第二份物理文件。
- 解除最后一个 Memory 关系后自动物理删除 Photo。
- 客户端单方面判断“无引用”后直接删除文件。
- 删除数据库记录后，选择器缓存长期保留幽灵照片。
- 新规则反向清理历史原图。

## 13. 全局 UI 与风格原则

- 视觉基调：`Modern Museum + Warm Memory`，安静、清晰、有展览感和温度。
- 信息层级优先于装饰；核心内容是 Memory 与照片，不让控制按钮抢占注意力。
- 危险操作可发现但克制：首页 Stage 删除放入 `···` 菜单，确认阶段再明确危险性。
- 状态不能只靠颜色表达；选中、已用/未用、失败、取消等应结合图标、文字、边框或形态。
- 空状态提供原因和自然下一步，不使用死路式文案。
- Loading、成功、失败、空、禁用、选中、焦点等状态均应被明确设计。
- 保持现有设计 token、组件和布局体系；非必要不引入第二套 UI 库。
- Desktop 与 Mobile 都是正式体验，不把移动端视为仅“能打开”。
- 文案统一使用项目既有语气；同一概念保持一致名称：Stage、Memory、Workspace、Existing Photo Library。

## 14. 数据、安全与隐私约束

### 14.1 数据完整性

- 所有删除、解除关系和迁移必须保护现有生产数据。
- Stage 删除与 Memory 取消归类使用事务或等价原子机制。
- Photo 引用关系依赖数据库约束、事务或服务端校验保护，不能只靠 UI。
- 新增字段采用向后兼容迁移；旧记录能在新代码中正常读取。
- 数据迁移需说明回滚/恢复思路，不允许不可解释的批量数据重写。
- 任何缓存、索引或派生列表必须在关系变化后正确失效。

### 14.2 授权与隔离

- 每个读取、搜索、筛选、关系创建、封面设置、删除和上传接口都必须在服务端验证当前用户对 Photo、Memory、Stage 的权限。
- 不得通过猜测 ID 引用其他用户照片、把其他用户 Photo 加入 Memory，或探测其标题/Stage/引用信息。
- 引用阻塞提示只能暴露当前用户有权查看的对象信息。

### 14.3 文件安全

- 服务端验证文件真实类型、大小和必要的图片解码结果，不信任扩展名、客户端 MIME 或压缩声明。
- 拒绝非图片载荷、危险格式和超出服务端最终限制的优化文件。
- 存储键由服务端生成或严格验证；禁止客户端提供任意磁盘路径。
- 文件名展示需转义；不得把用户提供的文件名直接拼接为存储路径、HTML 或命令。
- 图片元数据处理遵循现有隐私策略；若当前链路会移除不需要的 EXIF/GPS 信息，应保持这一行为。
- Exhibit 文本按安全纯文本或经统一清理后的富文本渲染，防止 XSS。

### 14.4 错误与日志

- 对用户提供可行动的错误原因，对日志保留任务 ID、文件级状态和失败阶段。
- 日志不得记录照片二进制内容、敏感 URL、令牌或不必要的私人文本。
- 批量失败不能用单一异常吞掉逐文件结果。

## 15. 性能原则

- 图片网格使用缩略图或合适尺寸的派生资源，避免加载全尺寸图作为列表缩略图。
- 大量照片和 Stage 使用分页、渐进加载、虚拟化或现有项目等价模式，避免一次渲染/解码全部资源。
- 客户端压缩设置有限并发，特别关注 Mobile 内存峰值和主线程卡顿；必要时使用现有 Worker 能力，但不为此引入无关架构。
- 及时释放对象 URL、Canvas、中间 Blob 和取消任务资源，避免长会话内存泄漏。
- 搜索、状态筛选和 Stage 筛选避免 N+1 查询；多关系结果在数据层或查询层去重。
- 全局上传进度更新应节流到合理频率，避免每个字节事件触发全应用重渲染。
- 横向 Stage 滚动不应因图片加载造成卡片尺寸跳动。
- 所有优化需以当前项目结构和可测量瓶颈为依据，不进行与任务无关的提前优化。

---

## 16. 无障碍原则

- 所有交互可用键盘完成；焦点顺序合理，焦点样式清晰。
- 图标按钮必须有可理解的 accessible name，例如“打开 Stage 操作”“向右浏览一个 Stage”“取消上传某照片”。
- 菜单、对话框、图片选择器和全屏查看器使用正确语义，并管理打开/关闭后的焦点。
- 危险操作确认对话框不能只靠颜色表示风险。
- 图片应使用有意义的替代文本策略；纯装饰图正确隐藏。
- 状态变化（上传进度、失败、取消、选择数量）应以不过度打扰的方式提供给辅助技术；避免每个细粒度进度事件都朗读。
- 文本、选中状态和导航 active 状态满足项目采用的对比度标准，目标不低于 WCAG 2.1 AA。
- 点击/触摸目标适合移动端操作。
- 动画尊重 `prefers-reduced-motion`；Time Gear 和滚动平滑效果需提供减少动态版本。
- 缩放文本或浏览器放大后，核心操作不应被遮挡或截断。

## 17. 测试与验证要求

### 17.1 每个 Task 开始前

1. 阅读项目级 `AGENTS.md`、永久上下文和当前 Task。
2. 查找实际代码路径、数据模型、API、缓存边界和现有测试。
3. 运行或记录与当前功能直接相关的行为基线。
4. 明确当前 Task 的修改范围和不应变化的行为。

### 17.2 自动化测试层级

按变更风险选择，但不得省略关键行为：

- 单元测试：索引解析、引用判定、状态汇总、筛选语义、随机候选等纯逻辑。
- 服务/API 测试：授权、事务、引用安全删除、逐文件结果、关系去重。
- 数据库/迁移测试：旧数据兼容、约束、回滚/失败时一致性。
- 组件测试：选择状态、空状态、错误状态、取消、菜单和焦点行为。
- E2E/集成测试：跨页面上传、Stage 删除后 Memory 保留、Photo 跨 Memory 复用、Viewer 点击项打开。

修复行为缺陷时，优先添加能在修复前失败、修复后通过的回归测试。纯视觉部分提供稳定的人工验收路径，项目若已有视觉回归体系则纳入其中。

### 17.3 每个 Task 完成前必须执行

- `pnpm check`（若项目已有该标准命令；若脚本名称不同，先说明并执行等价的 typecheck/lint/build 检查）。
- 与当前 Task 直接相关的测试。
- 必要的数据库迁移验证。
- Desktop 和 Mobile 关键路径检查。
- 对本次改动进行代码质量自查；非平凡改动按项目规则执行代码审查。

不得用扩大范围的“全量修复”掩盖既有失败。必须区分：

- 改动前已经存在的失败；
- 本次改动新引入的失败；
- 因当前 Task 正确改变行为而需要更新的测试。

### 17.4 跨任务最终回归矩阵

全部 Task 分别验收后，再执行一次整体验证：

- Viewer 点击任意展品从该图打开。
- 删除 Stage 后 Memory 全部保留并未归类。
- 有引用 Photo 无法删除；无引用且人工确认后物理删除。
- Stage Cover Selector 不显示已删除 Photo。
- 上传逐文件容错、跨路由持续、单张/整批取消正常。
- 新上传与 Existing Photo Library 可混合选图。
- Photo 跨 Memory 复用且不复制物理文件。
- 未处理 Photo 不自动删除。
- 20 个 Stage 横向浏览尺寸与箭头行为稳定。
- Exhibit 元数据按关系隔离。
- 顶部导航状态清楚。
- Time Gear 可随机无图 Memory，仅 0 Memory 时显示空状态。

## 20. 推荐顺序与开发节奏

### 20.1 顺序

```text
10A Viewer 点击项定位
→ 10B Stage 删除语义
→ 10C Photo 引用安全与物理删除
→ 10D Stage Cover Selector
→ 10E 上传管线与全局进度
→ 10F Workspace + Existing Photo Library
→ 10G Stage 横向浏览
→ 10H 展品标题与说明
→ 10I 导航反馈 + Time Gear
```

顺序依据：

- 先修复边界清晰的独立缺陷；
- 再固定 Stage 与 Photo 的删除生命周期；
- 在删除不变量稳定后重做封面选择；
- 随后建立上传生命周期；
- 最后基于稳定 Photo 模型建设组织与复用能力；
- 横向浏览、展品元数据和导航/随机状态作为后续独立体验增强。

### 20.2 推荐节奏

每个 Task 使用一个独立分支或至少一个清晰 checkpoint：

```text
Day/Iteration N
├── 上午：只读调查、基线、实施
├── Codex：检查、测试、自查、完成报告
├── 用户：按报告执行人工验收
├── 若失败：只修当前 Task，再验收
└── 通过：commit / tag / checkpoint，再开启下一 Task
```

对于 10E、10F、10H 等非平凡数据/状态任务，建议预留完整迭代，不与其他 Task 同日混合提交。若一个 Task 内部过大，应在不改变该 Task 对外验收边界的前提下拆成多个内部 commit，但仍只在整体达到当前 Task 验收标准后请求用户验收。
