# Personal Memory Palace V1
## 个人记忆宫殿 / 人生长廊

---

# 1. 项目愿景

Personal Memory Palace 是一个用于保存、整理和重新体验个人经历的数字人生博物馆。

用户通过照片和自己撰写的文字，将人生中的经历保存为一个个 Memory。

多年以后，用户可以重新进入这座“人生长廊”，看到过去的照片和当时留下的文字，从而重新回忆：

- 当时发生了什么；
- 当时和谁在一起；
- 当时自己是什么状态；
- 为什么这一刻值得被保存。

这个产品不是普通相册，也不是日记软件。

它更接近：

> 一座由自己亲手建立、并随着人生不断扩建的私人数字博物馆。

长期目标是：

> 让每个人都可以拥有一座属于自己的人生博物馆。

但 V1 **只服务单一拥有者，不开发完整多人平台。**

---

# 2. 核心产品理念

整个产品必须围绕以下原则设计。

## 2.1 记忆，而不是照片，是核心对象

照片是触发记忆的重要媒介，但产品保存的不是单纯图片。

核心对象是：

```text
Memory
```

一个 Memory 可以：

- 只有 1 张照片；
- 有多张照片；
- 表示一个瞬间；
- 表示一次旅行；
- 表示一次聚会；
- 表示人生中的一段经历。

因此：

```text
照片 ≠ Memory
```

而应该理解为：

```text
Memory
├── 照片
├── 文字
├── 人生阶段
└── 与其他 Memory 的关联
```

---

# 3. 产品隐喻

整个产品采用“私人现代艺术馆 / 人生博物馆”的视觉隐喻。

对应关系：

```text
用户的人生
=
博物馆

人生阶段 Stage
=
展厅 / 收藏册

Memory
=
一场展览

Memory 中的照片
=
展品

Story
=
展览说明 / 当时留下的故事

Memory 关联
=
不同展览之间的通道
```

这是整个 UI 和产品体验的基础。

---

# 4. 核心情绪

用户进入网站时，不应该感觉自己进入：

- 数据库；
- 相册管理器；
- 后台管理系统；
- 社交平台。

而应该感觉：

> 我进入了一座收藏着自己人生的长廊。

整体视觉语言：

```text
Modern Museum
+
Warm Memory
+
Future Archive
```

即：

现代艺术馆的秩序和留白  
+  
私人回忆的温度  
+  
少量未来科技感

---

# 5. V1 的核心目标

V1 是一个：

> **可以真实运行、部署到公网，同时未来可以继续演化的功能原型。**

第一阶段不是为了建设完整平台。

最重要的是验证：

> “人生长廊 + 随机遇见过去 + Memory 展览”这个体验是否真正成立。

因此第一阶段重点在：

```text
体验
>
功能数量
>
平台能力
```

---

# 6. V1 核心闭环

V1 必须完整支持以下闭环：

```text
上传照片
↓
进入照片整理台
↓
选择若干照片
↓
创建 Memory
↓
添加标题和 Story
↓
选择人生阶段（可跳过）
↓
保存
↓
Memory 出现在人生长廊
↓
未来通过阶段浏览或随机时间齿轮重新发现
↓
进入 Memory 展览
↓
重新看到照片和当时的文字
```

如果这个闭环流畅，V1 就已经成功。

---

# 7. 核心对象：Memory

Memory 是整个系统最重要的数据对象。

V1 中每个 Memory 至少支持：

```text
id

title

story

cover_image

gallery_images

stage

related_memories

created_at

updated_at

visibility

deleted_at
```

---

## 7.1 Title

Memory 标题。

例如：

```text
第一次来到爱丁堡
```

或：

```text
我们最后一次所有人都在一起
```

---

## 7.2 Story

Story 是一整段完全自由的纯文字。

不得设计固定模板，例如：

```text
发生了什么：
我的感受：
未来寄语：
```

禁止这种强制结构。

用户必须可以自由写：

```text
那天其实没有发生什么特别大的事情，
但是后来才意识到，
这是我们最后一次所有人都在一起……
```

V1 只支持纯文本。

暂时不做：

- Markdown；
- 富文本；
- 图片文字混排；
- 复杂排版。

---

## 7.3 Photos

一个 Memory：

```text
1 张照片
```

和：

```text
30 张照片
```

都必须合法。

Memory 是“一场展览”，而不是“一张照片”。

---

# 8. 照片是创建 Memory 的入口

创建 Memory 的流程必须从照片开始。

不要首先向用户展示：

```text
新建 Memory 表单
```

正确流程：

```text
上传照片
↓
整理照片
↓
选择照片
↓
创建 Memory
```

照片是用户回忆经历的触发点。

---

# 9. 照片整理台 Photo Workspace

用户可以一次上传大量照片。

例如：

```text
50 张旅行照片
```

上传后不能自动生成一个 Memory。

先进入：

```text
Photo Workspace
```

---

## 9.1 布局

使用传统、清晰的缩略图网格。

例如：

```text
[照片] [照片] [照片] [照片]

[照片] [照片] [照片] [照片]
```

---

## 9.2 操作

至少支持：

- 批量上传；
- 缩略图浏览；
- 多选照片；
- 取消选择；
- 显示已选择数量；
- 用选中照片创建 Memory。

例如：

```text
已选择 12 张照片

[创建 Memory]
```

---

## 9.3 用户自己决定如何拆分

系统不要：

- AI 自动分组；
- 自动识别事件；
- 自动按照 EXIF 分类。

用户自己决定：

```text
照片 1–8 → Memory A

照片 9–17 → Memory B

照片 18–30 → Memory C
```

---

# 10. 图片元数据原则

V1：

**不读取 EXIF。**

不要自动读取或使用：

- GPS；
- 拍摄地点；
- 相机型号；
- 镜头；
- 拍摄时间；
- 其他 EXIF 信息。

记忆的意义由用户定义，而不是系统推断。

---

# 11. 图片存储策略

照片用于网页浏览，而不是作为专业摄影原片库。

上传时：

默认生成经过优化的网页展示版本。

同时给用户一个选项：

```text
□ 同时保留原始图片
```

因此理论结构：

```text
上传图片
├── Web optimized version
└── Original version（可选）
```

V1 不需要支持 RAW。

优先支持常见图片格式，例如：

```text
JPEG
JPG
PNG
WebP
```

具体图片压缩参数由开发者根据网页体验和存储成本选择。

不要进行明显损害网页观看质量的过度压缩。

---

# 12. 人生阶段 Stage

Stage 是用户自己创建的人生阶段。

系统不要预设：

- 童年；
- 中学；
- 大学；
- 工作；
- 婚姻；
- 旅行。

因为人生不应该由软件定义。

用户自己创建，例如：

```text
大学本科

英国交换

摄影成长

科研探索

那段夏天
```

---

# 13. Stage 不是严格文件夹

Stage 是组织 Memory 的主要入口，但不是唯一结构。

Memory 可以：

- 属于一个主要 Stage；
- 关联其他 Stage；
- 与其他 Memory 建立关联。

概念上更接近 Obsidian：

```text
Stage A
   ↘
    Memory
   ↗
Stage B
```

但 V1 不需要真正实现复杂图谱可视化。

---

# 14. 未归类 Memory

创建 Memory 时：

系统应该推荐用户选择 Stage。

但：

**不强制。**

必须允许：

```text
未归类 Memory
```

因为整理不能成为记录的阻碍。

之后用户可以重新归类。

---

# 15. Memory ↔ Memory 关联

V1 支持手动关联 Memory。

例如：

```text
第一次拍银河
↕
第一次买天文设备
↕
第一次参加天文摄影活动
```

关联是双向还是单向，可以由开发者根据实现简单性决定，但用户体验上必须能从一个 Memory 看到相关 Memory。

V1 不需要：

- 自动推荐关联；
- AI 关系发现；
- Obsidian 式动态图谱。

---

# 16. 首页：人生长廊

首页是整个产品最重要的页面之一。

它不应该首先展示：

```text
最近上传
统计
管理面板
数据表
```

进入网站的感觉应该是：

> 进入自己的人生长廊。

---

# 17. 人生阶段展示方式

V1 中 Stage 采用：

> 收藏册 / 书架式视觉。

而不是普通按钮或者 Windows 文件夹。

例如：

```text
人生长廊

[大学本科]

[摄影成长]

[英国交换]

[旅行]
```

每个 Stage 像：

- 一本收藏册；
- 一本人生档案；
- 一个展厅入口。

---

# 18. Stage Hover 动画

这是 V1 的特色视觉交互之一。

鼠标悬停在 Stage 上时：

从收藏册附近伸出约 3 张代表照片。

概念：

```text
          [照片]

   [照片] [收藏册] [照片]

          大学本科
```

动画应该：

- 克制；
- 平滑；
- 高级；
- 不夸张；
- 不做游戏式弹跳。

照片可以来自该 Stage 中的 Memory。

V1 可选择：

- 最近照片；
- 固定代表图；
- 随机照片。

开发者选择最简单、稳定的实现。

---

# 19. 随机回忆：Time Gear

随机回忆是 V1 的核心体验之一。

用户进入人生长廊时，应明显看到：

```text
时间齿轮
```

它是一个具有轻科技感的视觉装置。

V1 不需要复杂 3D。

只需要：

```text
时间齿轮
↓
点击
↓
旋转动画
↓
随机选择一个 Memory
↓
进入该 Memory
```

---

# 20. 随机算法

V1 必须：

**完全随机。**

不要根据：

- 时间；
- 浏览次数；
- 重要程度；
- 标签；
- 用户行为；
- 推荐算法；

进行加权。

逻辑：

```text
所有有效 Memory
↓
随机抽取 1 条
```

纯粹的偶然性本身就是体验。

未来可以增加：

```text
当年今日
```

但 V1 不实现。

---

# 21. Memory Detail / Exhibition

进入一个 Memory 后，用户看到的应该是一场“小型展览”。

基本结构：

```text
主视觉照片

Memory 标题

Story

照片画廊

相关 Memory

关联人生阶段
```

---

# 22. Memory 是“一场展览”

不要按照：

> 一张照片 + 一段说明

设计。

正确理解：

```text
Memory
=
完整经历

照片
=
展览中的展品
```

因此：

一条 Memory 可以展示很多照片。

UI 应该让多图浏览舒服。

---

# 23. Memory 的补充记录

Memory 创建之后不是永久封死。

未来用户重新查看时，可以：

> 添加新的感想或补充。

原则：

不要简单覆盖过去的文字。

长期结构需要支持：

```text
Original Story

Later Notes
```

例如：

```text
2026：
当时留下的记录

2031：
五年后重新看到时的想法

2036：
十年后的补充
```

V1 可以先实现最基础的 Later Note。

每条补充应保存自己的创建时间。

---

# 24. 搜索

V1 提供基础关键词搜索。

搜索范围：

```text
Memory Title
+
Memory Story
```

不需要：

- 语义搜索；
- AI；
- 标签搜索；
- 人物搜索；
- 地点搜索；
- 高级筛选。

---

# 25. 删除机制

禁止 Memory / Stage 一键永久删除。

流程：

```text
删除
↓
回收站
↓
恢复
或
永久删除
```

V1 应至少支持：

- 移入回收站；
- 恢复；
- 永久删除。

---

# 26. 分享设计

网站默认是：

```text
私人博物馆
```

但用户可以邀请朋友参观。

分享出去的不是单独设计的另一个页面。

朋友看到的应该仍然是：

> 用户自己看到的那座人生博物馆。

即：

```text
同一个视觉系统
+
同一套人生长廊
```

区别只在于：

```text
Owner View
=
完整内容 + 编辑能力

Visitor View
=
允许分享的内容 + 只读
```

---

# 27. 分享范围

用户需要自己选择：

> 哪些内容允许访客看到。

因此：

Memory 应具备公开状态，例如：

```text
private
shared
```

Stage 的访客展示内容必须由其中允许分享的 Memory 决定。

不能因为 Stage 可见就自动暴露全部私密内容。

---

# 28. 分享访问方式

V1 支持两种模式：

```text
公开分享链接
```

以及：

```text
分享链接 + 访问密码
```

用户创建分享时自行选择。

V1 不需要：

- 好友系统；
- 关注系统；
- 评论；
- 点赞；
- 社交关系。

---

# 29. V1 单用户原则

V1 只服务一个拥有者。

第一阶段不要开发：

- 用户注册；
- 多租户；
- 多用户博物馆创建；
- 用户主页系统。

但是：

核心代码不要把未来扩展堵死。

例如数据结构和 service 层应避免大量硬编码：

```text
only_user
```

未来应该可以增加 User 层而不用整体推翻。

---

# 30. 公网部署

V1 最终必须可以：

```text
通过真实网址访问
```

不能只停留在：

```text
localhost
```

目的：

- 自己电脑访问；
- 手机访问；
- 朋友通过分享链接参观。

---

# 31. Owner 安全

虽然 V1 不做完整注册系统，但由于网站部署到公网，并包含编辑能力：

**管理和编辑入口不能完全公开。**

开发者应选择最简单、可靠的单用户保护方式。

目标：

```text
Owner
→ 可以编辑

Visitor
→ 只能浏览允许分享内容
```

不需要复杂 OAuth 或用户平台。

---

# 32. 响应式设计

电脑与手机都必须可用。

但主要用途不同。

## Desktop

重点：

- 批量上传；
- 照片整理；
- Memory 创建；
- 人生阶段管理；
- 关联管理；
- 深度浏览。

## Mobile

重点：

- 浏览；
- 随机回忆；
- 阅读 Memory；
- 简单编辑；
- 分享给朋友。

它不是实时记录工具。

因此 V1 不需要调用手机相机直接拍摄。

---

# 33. 产品不是实时记录软件

核心工作流：

```text
经历发生
↓
照片产生
↓
之后整理
↓
赋予故事
↓
进入人生博物馆
```

而不是：

```text
事情发生
↓
立刻打开网站
```

设计时不要把产品做成 Day One 或即时日记类应用。

---

# 34. Demo 数据

第一次运行项目时不要只有空白界面。

项目中应该包含少量独立 Demo 数据，用来立即展示：

- 人生阶段；
- Memory；
- 多图 Memory；
- 随机回忆；
- hover 照片；
- 相关 Memory。

但 Demo 数据必须：

```text
与用户真实数据完全隔离
```

并且可以方便关闭或清除。

---

# 35. 视觉设计规范

核心视觉：

```text
Modern Museum
+
Warm Memory
+
Future Archive
```

---

## 35.1 Modern Museum

使用：

- 大面积留白；
- 清晰层级；
- 简洁字体；
- 克制边框；
- 展馆式空间布局；
- 高质量照片作为主要视觉元素。

---

## 35.2 Warm Memory

不能过度冷淡。

可以通过：

- 暖色照明感；
- 柔和背景；
- 轻微纸张/材质感；
- 舒适文字排版；

增加温度。

---

## 35.3 Future Archive

科技感应主要体现在：

- 时间齿轮；
- 动画；
- 微交互；
- 时间 / 记忆相关视觉符号。

不要使用：

- 赛博朋克 HUD；
- 大量霓虹；
- 蓝色全息界面；
- 游戏化科技 UI。

---

# 36. V1 固定视觉主题

第一版只维护：

```text
1 套主题
```

不做：

- Dark Mode；
- Light / Dark 切换；
- Theme Editor。

把设计资源集中在一个高质量视觉系统上。

---

# 37. 国际化

V1 UI：

```text
中文
```

但代码结构应预留国际化能力。

要求：

避免把所有 UI 字符串散落硬编码在组件内部。

未来应能够增加：

```text
English
```

而不重写页面。

V1 不需要真正做语言切换。

---

# 38. 技术选型原则

具体技术栈由 Codex / 开发者选择。

不要因为这份文档预先锁定：

- React；
- Vue；
- Python；
- Node；
- Supabase；
- Firebase；
- PostgreSQL；
- 其他具体技术。

开发前先基于以下原则选择。

优先级：

1. V1 开发效率；
2. 公网部署简单；
3. 图片上传方便；
4. 数据结构清晰；
5. 未来可继续发展；
6. 成本低；
7. 代码容易阅读；
8. 不过度工程。

---

# 39. 技术架构原则

虽然是原型，但必须：

> 可以演化，而不是一次性 Demo。

建议至少明确分层：

```text
UI / Components

Domain / Business Logic

Data Access

Image Storage

Database
```

避免：

- 所有代码写在一个文件；
- UI 直接操作数据库；

# 45. V1 验收标准

- 能从图片中选择一部分；

- 能选择 Stage；
- Stage 可以为空；
- 能创建 Memory 关联。

### 浏览

- 首页有人生长廊视觉；
- Stage 使用收藏册/书架隐喻；
- Stage hover 至少可显示三张照片；
- 能进入 Stage；
- 能进入 Memory；
- Memory 多图展示正常。

### 随机

- Time Gear 可以点击；
- 有基础旋转动画；
- 每次从全部有效 Memory 中随机抽取。

### 搜索

- 可以搜索 Memory 标题；
- 可以搜索 Story。

### 删除

- 删除后进入回收站；
- 可以恢复；
- 可以永久删除。

### 分享

- Owner 可以决定哪些 Memory 对访客可见；
- 访客看到与 Owner 相同视觉体系；
- 访客不能编辑；
- 支持仅链接访问；
- 支持链接 + 密码。

### 设备

- Desktop 可正常使用；
- 手机浏览和基础操作正常；
- 页面响应式。

### 部署

- 可以部署到公网；
- 不能只在 localhost 工作。

# 46. Codex 执行原则

## 46.1 不扩大 Scope

如果文档明确写：

```text
Future / V2 / V3
```

则：

**不要实现。**

---

## 46.2 优先完整闭环

优先保证：

```text
上传
→
整理
→
创建
→
浏览
→
随机回忆
```

完整运行。

不要因为某个动画还不完美而阻塞核心流程。

---

## 46.3 不进行无关架构重构

架构只需要支持：

```text
V1 可用
+
以后能发展
```

不要为了几十万用户规模预先建设复杂系统。

## 46.4 技术选型前先给出简短 Architecture Decision

开始编码前只需要说明：

```text
选择什么技术

为什么

部署方式

数据库

图片存储
```

控制在简短范围。

不要输出长篇架构论文。

## 46.5 默认自主决策

# 47. 设计判断原则

如果设计过程中出现不确定：

优先问：

> 这个决定是否增强“回到过去”的感觉？

而不是：

> 这个功能是不是更高级？

整个项目最核心的不是技术炫技。

而是：

```text
十年后的某一天，

我打开网站，

随机看到一张自己曾经和朋友拍下的照片，

读到当时的自己写下的一段话，

然后突然重新想起：

那天发生过什么。
```

如果这个体验成立，

这个产品就已经实现了它最重要的价值。

# 48. 项目最终定位

Personal Memory Palace 不是：

```text
Photo Manager

Journal

Social Network

Cloud Drive

AI Diary
```

而是：

> **一个让人亲手建造属于自己的人生博物馆，并在未来重新遇见过去的数字空间。**

V1 的任务不是完成这座博物馆。

V1 的任务是：

> **建造第一条真正可以走进去的人生长廊。**
